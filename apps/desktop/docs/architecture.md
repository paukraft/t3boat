# How t3boat works

Internals. For what t3boat is and how to install it, see the [README](../../../README.md).

```
T3 Code ──ws──> localhost proxy (t3boat) ──https/wss──> T3 server on a Boat sandbox
                    │                                     └─ watchdog: stops the sandbox when idle
                    └─ boat CLI: new / resume / host / exec / delete
```

- **Machine**: a Boat sandbox running the T3 server pinned to your desktop app's version, as a systemd user service bound to loopback. Boat relays a public HTTPS URL to it; T3's own pairing auth protects it.
- **Proxy** (`src-tauri/src/proxy`): one `http://localhost:<port>` per machine; that is the address T3 Code pairs with, so a new sandbox IP after resume never matters. The proxy is its own auth server towards T3 Code and uses its own long-lived token upstream.
  - Awake: frames pass through (minus `directEndpoints`, which would let T3 Code bypass the proxy). Snapshot-style subscriptions and some reads are recorded, and the images T3 Code loads are kept on this computer (`proxy/assets.rs`).
  - Asleep: answers pings, probes, config and other recorded subscriptions, and serves the shell and the chats from the state captured as the machine went to sleep, so opening a chat does not wake it. Images shown before stay visible.
  - Anything else wakes the machine: `boat resume`, then the held request goes upstream, then the socket closes so T3 Code reconnects to the live server and resyncs. A message sent to a chat is accepted at once instead, since a wake outlasts T3 Code's 15 s slow-request warning: it shows as sent, wakes the machine and goes upstream before T3 Code reconnects; one the server refuses is reported as a notification. Only the side information T3 Code asks for on its own as it starts and as a chat opens (git status, branch, terminals, servers, the pull request's badge and checks, linked chats, the count of older chats, the branch list, the changed-files count) never does: it is shown as last seen, and with nothing recorded it stays unanswered until the machine wakes for something else. Worktree setup progress, a chat's preview tabs and their events are never shown from a recording (a stale one would hold Send, or close or reopen tabs). What T3 Code asks for on its own but a person also waits for is shown as last seen too, but wakes the machine when never seen: the linked machines (Send), a pull request's details (a quick merge, the checks popover), a related chat's title, the automations and the archived chats (their settings pages), the chats under "Show more", the files of a commit or of uncommitted changes, an MCP app's tool definition and resources (a click in the app, an approved download), the voice status of the machine dictation goes to (a mic click). Images never do either: one never seen on this computer shows as unavailable until the machine is next up. A finished command's output is kept the first time its row is expanded and shown from then on; one never expanded wakes the machine.
- **Streams** (`proxy/media.rs`): device and browser-preview streams pass through while the machine runs, close codes included. T3 Code opens them with a ticket the proxy issues itself and keeps retrying while one is on screen, so a stream never wakes a sleeping machine (it answers 503) and only input in it (a click, a key) counts as using the machine: watching does not keep it up. Dictation's `/ws/voice` is relayed the same way but wakes the machine: a person opened it. The loopback tunnel (`/api/preview/tunnel`, the machine's localhost pages in a preview) is relayed the same way and never wakes the machine: T3 Code's desktop app opens one on its own with every connection, retrying until it learns whether the machine shares this computer's loopback. Traffic through it either way (what the page sends, and what it is sent: server-sent events, hot reload) counts as using the machine only within 30 minutes of the person's last other use of it, a message sent while it slept included; what the page is sent only keeps it up, so recorded answers still hold (a diff reopened after a sleep doesn't wake it): an open preview keeps the machine up while someone is around, and one left open (hot reload, polling) stops counting 30 minutes after, so the machine sleeps after the usual 3 idle minutes. A sleeping machine refuses it as T3 refuses a port nothing listens on, which is true there. A socket T3 adds is relayed like a stream until known, since one T3 Code retries on its own would keep the machine up. A refusal from the machine reaches T3 Code with its headers: they say what it means.
- **Linked** (`machine/link.rs`, `proxy/link.rs`): with linked environments on in T3 Code (Settings → Labs), every machine is linked into the desktop app's own T3 server through the proxy, with full access as the ceiling, so agents on this computer can work on it (`delegate_task`, the thread tools) with nothing to set up. Links last 30 days; each wake renews one in its last week. The link's status probe is answered from the last descriptor and never wakes the machine; a tool call does, and counts as using it. The handshake that opens a link's MCP session is given 3 s by T3, less than a wake can take, so for a sleeping machine the proxy answers it itself: the call that follows waits for the wake, the machine refuses the unknown session and T3 opens a real one.
- **T3 Connect** (`machine/connect.rs`): T3's own route for other devices (its phone app, a browser), a tunnel the machine dials out to Cloudflare under a stable hostname. "Turn on" runs T3's `t3 up --connect --headless --yes` on the machine, opens its sign-in page here and waits until the machine is reachable, then turns on "Hold webhooks while offline": T3 Connect's relay keeps a webhook sent to a sleeping machine (up to 24 h) and delivers it as the machine wakes. The tunnel comes back by itself on every wake. Nothing wakes a sleeping machine for a phone: only t3boat on this computer wakes it. Provisioning names the machine in `/etc/machine-info`, so other devices show its t3boat name, not the sandbox's hostname.
- **Watchdog** (`src-tauri/src/machine/watchdog.mjs`, on the sandbox): the machine decides when to sleep, so it finishes its work and then sleeps even with the laptop closed. Idle = no agent run in flight, no sustained CPU use (a build), no "stay awake", no work due within 5 minutes, and nobody using it for 3 minutes: through t3boat, or in T3 from any other client (a phone through T3 Connect), seen as orchestration events only a person causes (opening a chat, pinning, archiving, ...). If T3 stops answering it counts as busy for at most 30 minutes; until it first answers after a boot it is starting, not failing. Before stopping it drains: publishes a manifest of orchestration high-water marks, the proxy captures that state and acks, the watchdog stops at that sequence (`boat stop <id>`: by id, as a service has no `BOAT_ID` for `self`) and says so. Only its tick stops it, or this app once the watchdog agrees on a fresh check (see Overdue sleep), after all the idle checks above, so whatever calls the sleep off in time (an agent starting, work due, T3 not answering) wins. The disk is saved as a Boat snapshot at every sleep. When this app acks the drain, the watchdog stops on its next tick and this app saves it once Boat reports the sandbox stopped (`boat snapshot <id>`: ~2 min, billed nothing, a wake meanwhile doesn't wait for it); with no ack within 45 s (closed laptop, app quit, its capture failed) the watchdog saves it first, awake (`boat snapshot <id>`, given up after 10 min; any use meanwhile calls the sleep off), then stops on a later tick; this app, if it comes back meanwhile, captures the drain then too. A save called off runs on: no stop and no second save until it ends. A run stopped at a prompt only a person answers (an approval, or a question T3 marks blocking) is not in flight: nobody pays while it waits. Unless T3 counts anything else as background work meanwhile (a command or tool still running, from this run or an earlier one; a background command in the provider's task list; a provider's own subagent), less the tools a pending prompt holds up: T3 lists no background work while a run is active, so the watchdog reads it from T3's database. So an approval asked by a provider's own subagent, or with background work still running, keeps the machine up. Turning on T3 Connect still stops for it, and a resize waits for the next sleep: the T3 restart would expire it. Deleting the machine does not wait for it. An ordinary question survives the sleep, T3 takes the answer as a message. An approval survives a warm resume (Boat keeps the stopped VM about 10 minutes, not guaranteed); after a cold one T3 expires it and cancels the run, and a message goes on from there. A card only the user can answer (a secret, a link) does not make the machine idle: T3's shell can't tell the two apart, and a link card's agent works on; one left after its run holds nothing. A delegated child T3 runs as its own thread on the same machine counts by its own state, so a parent waiting on one that waits on a person holds nothing either; a provider's own background agent (Claude's, Codex's) or a child on another machine still holds it. A watched pull request holds it only while its checks run, as T3 marks it awaited; after that a person moves it next.
- **Overdue sleep**: a failed stop is not use, so the machine stays drained at the same manifest and this app's capture stays confirmed. Once its next tick finds it still idle (all the checks above), the watchdog reports its sleep broken; once the watchdog, checking again, agrees (and turns away use as for its own stop), t3boat stops it from this computer (`boat stop <id>`, retried every 2 minutes), serves T3 Code from that capture, and tells the user, once: with the laptop closed it might bill on. Only while t3boat runs. A stop from here that fails is handed back: the machine drains on as after the watchdog's own. Either way the watchdog retries its own stop once the sleep delay has passed since its own last one, so retries from here never put that off.
- **Scheduled work**: T3 runs automations, held webhook runs and an agent's resume after a usage limit on in-process timers, so on a sleeping machine they would not run, and T3 skips a daily automation it missed by over 10 minutes. The watchdog reports the next due time from T3's database; t3boat keeps it and wakes the machine 2 minutes ahead, for work that came due after the machine went to sleep (what came due while it ran had its chance). The watchdog then waits for it instead of sleeping. Only while t3boat runs: Boat cannot resume a sandbox on a timer.
- **Capture**: one shell snapshot, unfiltered, which serves every client whatever it asked to leave out; and the chats, one file each on this computer, named by thread id, thread sequence and snapshot encoding (`proxy/threads.rs`). A sleep fetches the files it is missing, most recent chat first, and deletes every other one: the files are the store, there is no index. It has 12 s for all of it, since the watchdog saves the snapshot itself, awake, when no ack comes within 45 s; a chat that did not make it wakes the machine when opened.
- **Capture freshness**: the proxy trusts its capture only when the watchdog accepted its ack, or was seen stopping, at the captured sequence and Boat's `stoppedAt` follows soon after. Otherwise (laptop closed while the machine ran) the first request that needs state wakes the machine once to resync. Recorded reads carry an epoch that moves on whenever an agent works or the user acts, so no outdated file or diff is served; recorded subscriptions (git status, terminals, ...) and the branch list a chat displays replay as last seen instead. The project's `t3.json`, which T3 Code reads on every chat open, follows the epoch too, so each sleep reads the recorded ones again: T3's editor saves over the file whatever it was shown, and a new thread's environment is decided from it. The automations T3 Code was shown are read again at each sleep as well: its editor saves every field of a task as it was shown. A branch search, a further page of branches and the one branch read T3 Code decides on (is this branch checked out in that worktree?) follow the epoch like any other read.
- **Expiry**: chats leave the store 3 days after they are settled, recordings 3 days after T3 Code last asked for them, images with the recording that points to them.
- **Resize**: Boat resumes a sandbox onto any size; an idle machine is moved right away and keeps its "keep awake", a working one (an agent or a build) moves when it next sleeps.
- **Upgrades**: on wake, a machine whose T3 version or provisioning scripts differ from the app's is re-provisioned (`provision.sh` is idempotent). A running machine on older scripts takes them in place, scripts only: T3 is neither installed nor restarted, so nothing working or waiting there is lost; settings it reads take effect at its next start, and a new T3 version waits for the next wake. Not while a snapshot save runs: restarting the watchdog would kill it. Nor while T3 can't be checked: a restarted watchdog would take that for T3 starting, not maybe mid-turn. A machine whose older watchdog can't stop it never sleeps, so it would never get the upgrade a wake brings. A new T3 version also drops the recorded streams and stored chats: they are in the old server's encoding.
- **Keep-alive**: Boat keeps a stopped disk 14 days; machines asleep 12 days get a short wake.
- **Trial lifetime**: a free trial refuses no-auto-stop, so a machine there wakes with the trial's longest lifetime (2 h). While it runs, t3boat pushes that back in its last 30 minutes (`boat extend <id> --ttl 7200`), as the sandbox's own key can't. With t3boat not running, a trial machine stops within 2 h.
- **Restore**: with t3boat not running for those 14 days the disk is gone. The snapshot saved at every sleep (`t3boat-<name>-<id>`, one of the plan's saved snapshots per machine) has no expiry: the next wake creates a new sandbox from it. The machine keeps its id, port and T3 environment; only its sandbox and addresses change.
- **Delete** (`app.rs`, the reaper): a deleted machine leaves the app at once; its sandbox and saved snapshot go as a pair on a list saved with the state, with those of a create that failed or that a quit cut short (its watchdog runs, and can save the snapshot, before the create is done). The reaper deletes each until Boat's own list confirms it gone after a delete, never on a delete's answer alone nor on a list alone (a failed list holds back no delete), retrying every minute and at every launch; a pair's snapshot only once its own sandbox is gone, since a live one's watchdog can save it again, and a sandbox only once a save of it running here ends: a sandbox left behind bills without limit, and Boat can be down for a while. Not confirmed after 15 minutes, the user is told how to delete it by hand; it keeps trying.
- **Projects** (`projects.rs`, `machine/projects.rs`): t3boat moves no code itself; it drives T3 Code's own flow through T3's API. "Add a project" (in a machine's details, or picked when creating one) does what T3's "Add to another machine" dialog does: reads the project and its `.env` files from the desktop app's server (t3boat holds its own read-only session there, "t3boat" under Settings → Connections), then `projectClone.start` on the machine, which clones over HTTPS and registers the project with progress in T3 Code, then `projects.writeFile` for the env files. Private repos need nothing extra: Boat signs every sandbox in to GitHub as the Boat account (`gh` with git's credential helper, renewed on each resume), which T3's clones and pushes use. The machine's projects are read from its shell when it runs or sleeps, so listing them never wakes it. Work goes back the way T3 Code does it: push or open a PR. Agents use `add_project` here, or T3's own tools through the link (`t3_project_clone`, `delegate_task`, `t3_thread_launch` with the machine's `environmentId`).
